# Isker: как работать с проектом каждый день (инструкция для начинающих)

Эта инструкция объясняет весь путь изменения: от правки на своём компьютере до публикации на сайте и отката.
Технические подробности — в [DEPLOYMENT.md](../DEPLOYMENT.md).

## Три места, где «живут» изменения

| Где | Кто видит | Как попадает туда | Автоматически или вручную |
|---|---|---|---|
| **Локально** — ваш компьютер (или облачная сессия Claude Code) | только вы | вы сохраняете файл | автоматически: страница обновляется сама за доли секунды |
| **Предпросмотр (preview)** — временный сайт для pull request | все, у кого есть ссылка | pull request с `[render preview]` в названии | вручную включаете один раз для PR, дальше каждый push обновляет его сам |
| **Продакшн** — настоящий сайт | все пользователи | слияние (merge) в ветку `main` + зелёные проверки | merge — вручную, деплой после зелёных проверок — автоматически |

Главное правило: **сохранение файла никогда не публикует сайт.** На продакшн попадает только то, что вы слили в
`main`, и только если все проверки прошли.

## 1. Открыть проект

На своём компьютере (нужны Git, Node.js 22, Python 3.12 и PostgreSQL 16 — или Docker):

```bash
git clone https://github.com/ksvtmr/isker.git
cd isker
```

В Claude Code на сайте (claude.ai/code) проект уже открыт: зависимости устанавливаются автоматически при старте
сессии (`.claude/hooks/session-start.sh`).

## 2. Запустить предпросмотр (локально)

Одна команда из корня проекта:

```bash
npm run dev:all
```

Если PostgreSQL не установлен, но есть Docker:

```bash
npm run dev:all -- --docker-db
```

Скрипт сам проверит Node, Python и свободные порты, установит недостающие зависимости, применит миграции базы данных,
загрузит демо-данные и запустит API и сайт. Остановить — `Ctrl+C`.

Без установки Node и Python (только Docker): `docker compose -f docker-compose.dev.yml up`.

## 3. Найти локальный адрес

Когда всё готово, в терминале появится:

```
Isker is running:
  App:       http://localhost:5173
  API docs:  http://localhost:8000/api/docs
```

Откройте **http://localhost:5173** в браузере. Вход: `demo@isker.local` / `IskerDemo2026` (ученик) или
`admin@isker.local` / `IskerAdmin2026` (администратор). Эти пароли — только для разработки.

> В облачной сессии Claude Code `localhost` — это компьютер в облаке, а не ваш. Ваш браузер его не откроет.
> Claude проверяет страницы сам (автоматический браузер). Чтобы посмотреть глазами — запустите проект у себя
> (шаги 1–3) или откройте предпросмотр pull request (шаг 9).

## 4. Попросить Claude Code внести изменение

Пишите обычным языком, что нужно и где. Хорошие примеры:

* «На странице /dashboard поменяй заголовок на "Мой прогресс" на всех трёх языках (ru/kk/en).»
* «Добавь в админке поле "телефон" для пользователя, с миграцией базы данных и тестами.»
* «Кнопка "Начать оценку" на телефоне выходит за край экрана — исправь и проверь в браузере.»

Полезно добавить в конце: «Запусти проверки и закоммить в текущую ветку, в `main` не пушь».
Claude работает в своей ветке (например, `claude/...`), а не в `main`.

## 5. Увидеть изменения без пересборки

При запущенном `npm run dev:all`:

* правка интерфейса (`frontend/`, `design-system/`) или переводов (`frontend/src/i18n/locales/{ru,kk,en}/`) — страница
  обновляется сама меньше чем за секунду, введённые в формы данные не теряются;
* правка сервера (`backend/app/`) — API перезапускается само примерно за 2 секунды, обновите страницу;
* изменили `package.json`, `backend/requirements*.txt` или `.env` — остановите (`Ctrl+C`) и снова запустите
  `npm run dev:all`;
* добавили миграцию базы данных — тоже перезапустите: миграции применяются при старте.

## 6. Запустить тесты

Быстрые проверки (то же самое запускает GitHub автоматически):

```bash
# Сервер: стиль кода, типы, безопасность миграций, тесты
cd backend && .venv/bin/ruff check app tests scripts && .venv/bin/mypy app \
  && .venv/bin/python scripts/check_migrations.py && .venv/bin/pytest -q && cd ..

# Интерфейс: стиль, типы, тесты (включая полноту переводов ru/kk/en), сборка
npm run lint && npm run typecheck && npm test && npm run build
```

Браузерные тесты (нужен запущенный сайт на :8000 с собранным интерфейсом, см. README «Quality checks»):

```bash
cd scripts/e2e && npm install && BASE=http://localhost:8000 node journey.mjs && BASE=http://localhost:8000 node languages.mjs
```

## 7. Сохранить изменения в Git

Работайте не в `main`, а в отдельной ветке:

```bash
git checkout main && git pull           # взять свежую версию
git checkout -b feature/my-change       # новая ветка для задачи
# ... правки ...
git status                              # что изменилось
git add -A
git commit -m "Коротко: что и зачем изменено"
```

Не добавляйте в Git файл `.env` (он уже в `.gitignore`) и никакие пароли или ключи.

## 8. Отправить на GitHub

```bash
git push -u origin feature/my-change
```

Затем на GitHub: появится кнопка **Compare & pull request** → **Create pull request**. Через несколько минут на
странице PR будут результаты проверок (вкладка **Checks**): зелёная галочка — всё в порядке, красный крестик —
что-то сломано, нажмите **Details**, чтобы увидеть ошибку.

## 9. Предпросмотр (preview) для pull request

Нужно: тариф Render с функцией Preview Environments (см. DEPLOYMENT.md, раздел 5).

1. Добавьте в название pull request текст `[render preview]`, например: `Новый заголовок дашборда [render preview]`.
2. Render создаст отдельный временный сайт **со своей отдельной базой данных** (данные продакшна не затрагиваются)
   и покажет ссылку в pull request и в панели Render.
3. Каждый новый push в эту ветку обновляет предпросмотр автоматически.
4. Сайт удаляется сам при закрытии/слиянии PR или через 3 дня без изменений.

Проверить предпросмотр можно командой: `bash scripts/smoke.sh <ссылка на предпросмотр>`.

## 10. Опубликовать на продакшн

1. Убедитесь, что все проверки в PR зелёные.
2. На GitHub нажмите **Merge pull request** (вручную — это и есть решение «публикуем»).
3. Дальше автоматически: GitHub ещё раз запускает проверки на `main` → Render ждёт, пока они пройдут → собирает
   образ → применяет миграции → запускает сайт → проверяет `/api/health` → переключает пользователей на новую
   версию. Обычно 5–10 минут.
4. Если какая-то проверка не прошла, Render **ничего не публикует**, а сайт продолжает работать на старой версии.
5. После публикации проверьте сайт: GitHub → **Actions** → **Smoke check (deployed site)** → **Run workflow**, или
   `bash scripts/smoke.sh https://<ваш-сайт>.onrender.com`.

## 11. Читать логи

| Что посмотреть | Где |
|---|---|
| Почему не прошли проверки | GitHub → pull request → **Checks** → нужная проверка → **Details**. При падении браузерных тестов внизу страницы запуска есть архив `e2e-failure` со скриншотами |
| Как прошла публикация | Render → сервис `isker` → **Events** (Building / Live / Failed и причина) |
| Ошибки работающего сайта | Render → сервис `isker` → **Logs** |
| Локально | в терминале с `npm run dev:all`: строки `[api]` — сервер, `[web]` — интерфейс; ошибки интерфейса — также в консоли браузера (F12) |

## 12. Откатить неудачную версию

1. **Сразу вернуть рабочий сайт:** Render → сервис `isker` → **Events** → найдите последнюю удачную публикацию →
   **Rollback**. Через 1–2 минуты работает предыдущая версия.
2. **Исправить в Git**, иначе следующий merge снова опубликует ошибку: на GitHub откройте слитый PR → **Revert** →
   создайте и слейте этот новый PR (или исправьте ошибку отдельным PR).
3. **База данных** откатом не меняется. Миграции Isker только добавляют данные, поэтому старая версия работает с новой
   схемой. Если миграция когда-нибудь удаляет данные, CI требует пометку «Destructive steps», а перед публикацией
   нужно сделать резервную копию (команда — в DEPLOYMENT.md, раздел 7).

## 13. Если что-то не работает

**Страница не обновляется сама (hot reload)**
* Проверьте, что `npm run dev:all` ещё работает (в терминале нет ошибки и `Ctrl+C` не нажимали).
* Открыт ли адрес **:5173**? На :8000 автообновления нет.
* В консоли браузера (F12) есть ошибка? Синтаксическая ошибка в файле останавливает обновление — исправьте её, и
  страница обновится.
* Меняли `.env`, `package.json` или зависимости — перезапустите `npm run dev:all`.

**`npm run dev:all` не запускается**
* «Port 8000/5173 is already in use» — закройте другой запущенный экземпляр или запустите на других портах:
  `API_PORT=8001 WEB_PORT=5174 npm run dev:all`.
* «Cannot connect to the database» — запустите PostgreSQL или используйте `npm run dev:all -- --docker-db`; проверьте
  `DATABASE_URL` в `.env`.
* «Python 3.11+ is required» / «node: not found» — установите нужную версию.

**Проверки на GitHub красные**
* Откройте **Details** у красной проверки и найдите первую ошибку. Запустите ту же команду локально (шаг 6).
* Можно попросить Claude Code: «CI в PR упал на проверке X, вот ошибка: … Исправь и запушь в ту же ветку».
* Не отключайте проверки, чтобы «стало зелёным», — они защищают продакшн.

**Публикация на Render не удалась**
* Render → **Events** → нажмите на неудачную публикацию: видно, на каком шаге (сборка, миграции, health check).
* Сайт при этом продолжает работать на предыдущей версии.
* Частая причина — не задана обязательная переменная (например, `ADMIN_PASSWORD`) в Render → **Environment**.
* Первый запрос к бесплатному сервису после простоя идёт около минуты — это не ошибка.

## Кратко: что автоматически, а что вручную

| Автоматически | Вручную (делаете вы) |
|---|---|
| обновление страницы при сохранении файла | запуск `npm run dev:all` |
| проверки CI на каждый push и pull request | commit, push, создание pull request |
| обновление предпросмотра при push в PR | включение предпросмотра (`[render preview]` в названии) |
| публикация `main` после зелёных проверок, миграции, health check | merge pull request в `main` |
| ежедневная smoke-проверка (если задан `PRODUCTION_URL`) | откат (Rollback) и revert |
